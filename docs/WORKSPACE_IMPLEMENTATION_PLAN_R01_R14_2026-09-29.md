# Company Workspace R01~R14 구현 계획

작성일: 2026-09-29. 이 문서는 **구현 전 조사와 계획**을 보존한다. 조사 대상은 Workspace 0.11.4와 연동되는 Company Agent이며, 이후 구현 상태는 [단계별 진행 기록](WORKSPACE_IMPLEMENTATION_PROGRESS_2026-09-29.md)과 [0.12.0 검증 기록](VALIDATION_0.12.0.md)을 따른다.

목표는 회사 PC의 기존 설정과 개인 Claude 환경을 유지하면서, 비개발자가 GUI로 업무를 끝까지 수행하고 기존 CLI 사용자도 익숙한 입력·모드 기능을 사용하는 것이다.

## 1. 조사 범위와 판단 기준

- 현재 `hermes` 작업 폴더의 실행기, Python 서버·CLI 연결, 웹 UI, Company Agent 코어·스킬·후크 및 관련 테스트를 읽었다. 기존 미커밋 변경도 현재 구현에 포함했다.
- 별도 공개 저장소의 로컬 체크아웃 `build/workspace-local-repository`는 `4bdc36aa1b6abfa1800bbb8c0c9af2214fc810f4`이며 작업 트리는 깨끗하다. 실행 관련 31개 파일은 현재 루트 소스와 바이트가 모두 같다.
- 시작·선택창 관련 6개 파일은 사용자가 지정했던 `dist/company-workspace-preview-0.11.1-20260928-214617/Company-Workspace`의 파일과도 해시가 같다. 폴더 이름만으로 내용이 구버전이라고 판단하지 않는다.
- 이번 작업은 정적 조사와 계획 작성이다. VBS, 실제 CLI 대화, 선택창, 개인 설정 변경, 테스트 재실행은 수행하지 않았다. 기존 검증 기록은 회귀시험 선정에만 사용했다.
- 오류를 보고한 다른 회사 PC의 실행 권한, 설치된 CLI·Company Agent 버전, 실제 출력은 아직 확보하지 않았다. 붙여넣은 UAC 진단과 성공 기록은 해결 후보의 참고 자료다.
- 아래 **확인**은 소스로 확인한 동작, **미확정**은 실제 실패 환경에서 검증할 원인이다. 완료 기준은 앞으로 충족할 조건이며 현재 통과했다는 의미가 아니다.

## 2. 기본 설계 방향

1. 우선 Python 로컬 서버 + Edge 앱 창 + 기존 Claude CLI 구조를 유지한다. 이번 요구만으로 전체를 Electron 등으로 다시 만드는 작업은 포함하지 않는다. OS 창 식별·알림의 기술 검증이 실패할 때만 작은 네이티브 호스트 대안을 비교한다.
2. Windows 프로세스 권한, Claude 도구 승인 모드, 업무 폴더 신뢰를 별도 상태로 관리한다. CLI의 auto 모드를 바꿔도 Windows 실행 권한 문제는 해결되지 않는다.
3. 실제 실행 컨텍스트와 목록 조회 컨텍스트를 분리한다. 공통 목록을 보거나 다른 폴더를 조회해도 현재 업무의 실행 폴더·모델·초안은 바뀌지 않는다.
4. 설치 발견, CLI가 보고한 목록, 실제 호출 성공을 구분한다. 이름이 있다는 이유로 사용 가능·권한 허용을 보장하지 않는다.
5. 반복 승인은 실제 CLI의 승인 정책 및 확인된 하네스 동작에서 줄인다. GUI가 임의로 모든 승인 요청에 허용을 반환하는 방식은 채택하지 않는다.
6. 업무 파일만 사용자가 고른 저장 위치에 둔다. 인증·서버 토큰·로그·대화 상태 등 내부 자료는 기존 상태 위치에 유지한다.
7. Workspace 수정과 Company Agent 수정은 별도 배포 단위다. 하네스 후크나 스킬 지침이 원인인 문제를 Workspace ZIP만 배포하고 해결 완료로 처리하지 않는다.

## 4. 항목별 구현 계획

### R01. WS-33 실행 실패

- **현재·차이:** `Start-CompanyWorkspace.ps1:11`부터 사용자 확인 → 일반 권한 재실행 → 최종 검사가 진행된다. `CompanyWorkspace.Startup.ps1:103`과 `CompanyWorkspace.NormalToken.cs:71`은 같은 사용자·세션의 정상 토큰만 허용하며 UAC-off 분기가 없다. 붙여넣은 예외 수정은 현재 배포 파일에 없다. 한편 `server.py:753`의 직접 Python 진입에는 동일 PowerShell 검사가 없다.
- **원인 확인:** 실패 배포본 버전·해시, 현재 토큰의 SID/세션/프로필·상승 상태·무결성 수준, 연결 토큰 조회 결과, UAC 상태와 native 오류 단계를 읽기 전용으로 확인한다. 오류 번호만으로 UAC-off를 확정하지 않는다. 레지스트리 값과 현재 로그인 토큰 상태도 함께 본다.
- **변경 방향·범위:** 기존 정상 경로를 유지하고, 정상 토큰이 없는 환경은 제한된 토큰 생성 후보와 같은 사용자 현재 권한 실행 후보를 비교하는 짧은 기술 검증을 먼저 한다. 제한 토큰은 표준 사용자와 동일하다고 가정하지 않고 CLI·프로필 접근·자식 프로세스까지 검증한다. 현재 권한 허용 후보는 실제 수행 권한이 높게 유지되는 정책 변경으로 명시하며 자동 채택하지 않는다. 결과를 근거로 대상 환경을 지원하는 정책을 결정하고 VBS/PowerShell/직접 Python 진입에서 일관되게 적용한다.
- **대상 파일·의존성:** `deploy/CompanyWorkspace.Startup.ps1`, `CompanyWorkspace.NormalToken.cs`, `Start-CompanyWorkspace.ps1`, 필요시 `local_app/server.py`; `Check-Workspace.ps1`의 고정 해시·진단 버전, 시작 문서·테스트. R03의 실제 사용자/CLI 컨텍스트를 공유한다. Windows 정책 자체를 변경하지 않는다.
- **완료 기준:** 대상 PC에서 설정 변경 없이 VBS → 화면 → 서버 → Claude 요청까지 실행된다. 다른 계정·SYSTEM·서비스 세션을 허용하지 않고 재실행은 최대 1회, 같은 실패 안내도 1회다. 대상 환경을 지원하지 못한 후보는 성공으로 보고하지 않는다.
- **검증:** 일반 계정, 분리 토큰 관리자, 실제 UAC-off 대상 환경, 프로필 불일치, API 거절, 재시작을 구분한다. 기존 startup/normal_token/diagnostic/reopen 테스트를 확장하고 실제 대상 PC 시험을 별도로 수행한다. 현재 권한 정책 결정은 후속 구현의 선행 의사결정이다.

Windows 공식 API에는 기존 토큰의 SID·권한을 제한하는 기능이 있다. 이는 후보의 존재를 뒷받침하지만 이 앱의 실행 성공이나 표준 토큰과의 동등성을 보장하지 않는다. [Microsoft CreateRestrictedToken](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken)

### R02. 경로 선택 Extra data 오류

- **현재·차이:** `server.py:472`는 `-NoProfile -STA`로 선택기를 실행하고 `478`에서 stdout 전체를 `json.loads`한다. `Pick-Path.ps1:83` 이후는 배열을 출력한다. 추가 JSON이나 다른 출력이 섞이면 실패할 수 있으나 실제 오염 원인은 미확정이다. 이미 Common Item Dialog와 DPI·소유 창 처리가 있으므로 선택창을 처음부터 다시 만들 필요는 없다.
- **원인 확인:** 정상·실패 시 종료 코드, 응답 건수·형태, stdout/stderr 경계를 비교한다. 경로 원문은 필요한 경우에만 로컬에서 확인한다. 현재 `-NoProfile`을 사용하므로 PowerShell 프로필을 원인으로 단정하지 않는다.
- **변경 방향·범위:** `success/cancel/error`, `paths`, 프로토콜 버전으로 단일 응답 계약을 정의한다. 결과와 진단 채널을 분리하며 stdout 오염이 반복되면 요청별 결과 파일 방식도 검토한다. 여러 응답 중 첫 JSON을 골라 성공으로 처리하지 않는다. 서버에서 타입·개수·선택 종류·경로를 검증하고 오류를 사용자 안내로 변환한다.
- **대상 파일·의존성:** `local_app/Pick-Path.ps1`, `WorkspacePicker.cs`, `server.py:pick`, `web/app.js`; R04 초기 폴더 인자를 함께 설계한다. P0.
- **완료 기준:** 정상 선택·취소·실패가 구분되고 원시 JSON 오류가 그대로 나타나지 않는다. 모든 종료 경로에서 선택창 잠금과 소유 창 자원이 정리된다.
- **검증:** 폴더 1개, 복수 파일, 한글·공백·이모지 경로, BOM/CRLF, 추가 stdout, 복수 JSON, 잘못된 schema, 시간 초과, 빠른 중복 클릭. 기존 picker/integration/native 테스트에 실패 fixture를 추가하고 실제 대상 PC에서 선택한다.

### R03. Company Agent·스킬 인식

- **현재·차이:** `harness_client.py:38` 이후는 서버의 Claude 설정 루트, 활성 설치 등록, 버전, 범위를 대조한다. `skill_inventory.py:126`은 등록된 코어에서 목록을 읽는다. 탐색 실패는 `capabilities.py:119`에서 일반적인 미확인 상태로 축약된다. CLI wrapper가 자식 프로세스에서만 설정 루트를 변경하면 서버의 판단과 달라질 가능성이 있다. 현재 PC에서 확인한 원인은 아니다.
- **원인 확인:** 실제 CLI 진입점·설정 루트·설치 ID·플러그인 활성화·등록 범위·코어 API 지원을 단계별 비교한다. CLI init 목록과 설치 목록을 분리해 어느 단계가 실패했는지 판별한다. project/local 설정 파일 선택과 병합 규칙도 installer·코어 계약에 대조한다.
- **변경 방향·범위:** 비민감 실행 컨텍스트를 공통 계약으로 전달하고 `등록 없음/비활성/설정 불일치/버전 불일치/API 미지원/조회 실패`를 구분한다. 하네스 관리 기능과 일반 스킬 메타데이터 탐색을 분리할 수 있는지도 검토한다. 임의의 다른 Python·다른 계정 설치·저장소 코어로 대체하지 않는다.
- **대상 파일·의존성:** `harness_client.py`, `skill_inventory.py`, `capabilities.py`, `bridge.py`, 카탈로그 UI. 필요한 경우 별도 Company Agent의 `native_runtime.py`, `skill_registry.py`. R01·R07과 공동 설계. P0 진단/P1 개선.
- **완료 기준:** 설치 발견/현재 범위 적용/CLI 보고/실제 호출을 구분해 보여준다. 다른 계정 설정을 섞지 않으며 기존 개인 설정과 설치를 보존한다.
- **검증:** 사용자·프로젝트 설치, 하위 폴더, custom config, 회사 wrapper, 구형 코어, 다중 등록, 비활성, 시간 초과 fixture. `test_workspace_skill_inventory.py`, `test_workspace_companion.py`, `test_workspace_capabilities.py` 확장 후 대상 설치에서 실제 요청 확인. 인증 상태 전체 해시 대신 앱이 소유하지 않은 설정에 대한 쓰기 여부·필요한 파일 해시를 확인한다.

### R04. 바탕화면 기본 저장 위치

`FlashWindowEx`는 창의 활성 상태를 바꾸지 않는 강조 API다. 이 앱에서는 정확한 창 식별과 브라우저별 동작 확인이 선행되어야 한다. [Microsoft FlashWindowEx](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-flashwindowex)

### R12. Stop hook 오류와 완료 상태

- **현재·차이:** 코어 `state.py:1260` 이후에 검증 상태와 최대 두 번 보정·진전 없음 중단이 구현되어 있다. `completion_feedback.py:12`는 현재 보정 지시를 보존하며, 사용자가 붙인 짧은 문구로 바꾸지 않는다. 설치판이 이 소스와 같은지는 미확정이다. `bridge.py:385` 이후는 일부 system 이벤트와 최종 result만 처리하여 후크 검증 상태를 별도 표시하지 않는다.

- **변경 방향·범위:** 코어에는 검증 의무와 실제 다음 조치를 유지하고 정상 확인/검증 실패/미확인/후크 장애를 분리한다. GUI는 증거가 있는 상태만 진행 안내로 보여준다. `result`가 도착했다는 이유로 업무 검증까지 성공으로 표시하지 않도록 전달 계약을 정의한다. 에러 문구 삭제나 hook 비활성화만으로 해결하지 않는다.
- **대상 파일·의존성:** 별도 코어의 `stop_feedback_hook.py`, `native_entry.py`, `company_agent/state.py`, `completion_feedback.py`; Workspace `bridge.py`, `server.py`, `web/app.js`. P0 진단/P1 개선. R13의 선택 대기, R14의 조회 분류와 연계한다.
- **완료 기준:** 정상 업무는 반복 안내 없이 끝난다. 미검증 업무는 미확인으로 끝나고 실제 오류는 이유를 남긴다. 질문 대기와 승인 불가를 성공이나 재실행 대상으로 잘못 처리하지 않는다.

Stop hook은 종료를 보류하고 모델에 다음 조치를 전달할 수 있으므로, 사용자에게 보인 오류 표제만으로 후크 프로세스가 실패했다고 확정할 수 없다. [Claude Stop hook 계약](https://code.claude.com/docs/en/hooks#stop-decision-control)

### R13. 중복 선택지·클릭 응답

- **현재·차이:** `app.js:137`과 `bridge.py:456`에는 AskUserQuestion의 선택·직접 입력·응답이 있다. 반면 `html-report/SKILL.md:48`은 디자인 10개를 채팅에 출력하고 AskUserQuestion으로 나누지 않도록 지시한다. `bridge.py:317`에는 stream/final 합치기와 동일 텍스트 제거가 이미 있다. 사용자의 두 메시지는 앞 문장이 달라 단순 동일 문자열 제거만으로 해결된다고 볼 수 없다.
- **원인 확인:** message ID, content index, request ID, turn ID, stream/assistant/result/Stop 보정 순서를 비교한다. 전송 중복인지 실제 재생성인지 구분한다. 텍스트 유사도만으로 정상 메시지를 숨기지 않는다.
- **변경 방향·범위:** 이벤트 재생은 ID로 한 번만 반영하고 최종 메시지는 해당 stream 블록을 확정한다. 의미가 같은 새 질문의 재생성은 하네스의 선택 상태를 수정한다. 10개 목록은 구조화된 선택 요청 계약을 추가해 한 번에 버튼/카드로 표시하는 안을 권장한다. 선택은 기존 대기 요청 응답 또는 정상 다음 사용자 메시지 중 해당 계약에 맞는 경로 하나로만 전달한다. 임의의 모든 번호 목록을 버튼으로 바꾸지 않는다.
- **대상 파일·의존성:** Workspace `bridge.py`, `server.py`, `history.py`, `web/app.js`; Company Agent `skills/html-report/SKILL.md`와 선택 상태/helper 계약. P1. R12의 보정과 R06 알림이 같은 질문을 중복 생성하지 않게 한다.
- **완료 기준:** 같은 질문은 한 번 보이며 클릭/직접 입력이 같은 업무 흐름으로 이어진다. 연속 클릭·재연결로 답이 두 번 전송되지 않고, 서로 다른 정상 질문은 보존된다. 선택 후 불필요한 재확인 없이 다음 단계로 간다.
- **검증:** stream+assistant+result 반복, 두 assistant 메시지, Stop 보정 재생성, 연결 복구·기록 재열기, 유사하지만 다른 질문, 10개 디자인, 자유 입력, 다중 선택, 오래된 요청·중복 응답. 기존 transport/frontend/question 회귀를 확장한다.

### R14. 반복 승인 줄이기

- **현재·차이:** `app.js:140`은 이번 요청만 승인한다고 안내하고 `bridge.py:469`는 1회 allow/deny만 반환한다. 코어 `execution_contract.py:345`의 자동 허용은 등록된 실행 경로의 두 메타데이터 명령으로 제한된다. `_words:19`는 파이프·리디렉션 등을 거절한다. 따라서 제시한 `--help 2>&1 | head -30`은 현재 허용 계약에 포함되지 않는다. 실제 PC에서 어느 계층이 승인을 요청했는지는 별도 확인이 필요하다.
- **원인 확인:** 동일 작업의 CLI 판단·하네스 hook·GUI request ID를 연계한다. 도움말/스킬 검색/목록 조회의 승인 횟수와 원인을 기록해 반복 탐색, 불필요한 셸 조합, 권한 유지 부재를 구분한다.
- **변경 방향·범위:** 제공된 runtime·스킬 메타데이터를 재사용해 불필요한 `--help`·경로 재탐색부터 줄인다. 필요 조회는 등록된 진입점의 명확한 읽기 전용 계약으로 제공한다. 실제 CLI가 지원하는 세션 범위 허용·권한 변경을 GUI에 연결하며 기존 deny·조직 정책을 유지한다. 작업 분류(read-only)와 실행 허가를 별개로 둔다. 자동 허용 확대는 검증한 명령/인자/범위에만 적용한다.
- **대상 파일·의존성:** `bridge.py`의 승인 응답·기능 협상, `server.py`, `web/app.js`; 필요시 별도 코어의 `execution_contract.py`, `native_runtime.py`, hook 계약·스킬 지침. P1. R10의 모드 상태와 R12의 변경 분류를 공유한다.
- **완료 기준:** 대표 보고서 흐름에서 이미 허용된 동일 조회가 반복 확인을 요구하지 않는다. 지원되는 계약으로 한시 허용한 조회는 해당 범위에서 0회 재승인, 실제 부작용 작업은 선택한 CLI 정책대로 처리된다. 모델이 만든 설명이나 명령 이름만으로 승인하지 않는다.
- **검증:** 등록된 도움말·메타데이터, 다른 실행 파일, 경로 위장, 파이프·출력 리디렉션·치환, 인자에 쓰기/전송 포함, deny/ask 정책, 권한 만료, 두 업무 간 유출, 질문 도구 유지. CLI+하네스+GUI 왕복으로 승인 횟수를 비교한다. `test_native_runtime.py`, `test_policy_feedback.py`, `test_completion_efficiency.py`, Workspace 승인 테스트를 확장한다.

5. **실패 처리:** CLI 미지원·연결 중단·후크 실패·승인 거절·검증 소진·알림 제한·연결 프로그램 없음. 불확실한 결과를 성공으로 바꾸지 않음.
6. **기존 자산 보존:** 인증·모델·MCP·스킬·메모리·지식·기존 업무에 대한 앱의 비의도적 쓰기가 없는지 확인. 정상 CLI 인증 갱신 등과 앱 변경을 구별하며 개인 내용을 공개 로그에 넣지 않음.
7. **격리 회귀:** 기존 Workspace 테스트 + 변경된 코어 관련 테스트 + 실제 Windows 수용시험을 구분해 기록. 테스트와 demo는 임시 프로필·업무 루트를 사용. 이번 문서는 이 시험을 실행한 결과가 아님.
8. **배포:** Workspace 저장소에는 Workspace 변경만, Company Agent에는 필요한 코어·스킬 변경만 반영. 구버전 코어에서도 가능한 기능과 추가 업데이트가 필요한 기능을 표로 제공. 배포본이 설치된 하네스를 자동 덮어쓰지 않음.
9. **번들·복구:** 신규 폰트·native 모듈·라이선스·정적 경로를 번들 허용 목록에 포함하고 내용·해시를 확인. 새 위치 기본값은 기존 세션을 이동하지 않으며 구버전으로 되돌려도 업무 파일이 남아야 함. 새 버전 번호는 실제 구현·검증 후 결정.
