# 0.23.20 응답성·실행 중 승인 모드 수정 검증

검증일: 2026-10-06. 비교 기준은 0.23.19(`8a6cdbc`)와 이전 0.23.20 수정본(`fbd4d27`)입니다. 앱 버전은 0.23.20을 유지합니다.

## 확인한 원인과 수정

1. 관리자 실행 시 WebView2가 사용하는 API 전달 경로에서 파일·스킬 목록 조회와 버튼 요청이 동일한 동시 실행 한도 4개를 사용했습니다. 느린 조회가 한도를 차지하면 버튼이나 승인 모드 변경도 대기했습니다. 이벤트 4개, 조회 4개, 버튼·제어 4개, 업로드 1개의 별도 한도를 사용하도록 수정했습니다. 전체 한도는 HTTP 연결 한도 16 이내이며, 기존 인증·동일 출처·Windows 권한 검사와 업로드 크기/임시 파일 제한을 유지합니다.
2. 실제 CLI의 첫 `system/init` 이후 전달하는 연결 이벤트에 `connected` 값이 없었습니다. 화면이 이 이벤트로 연결 상태를 교체하면서 작업 중 모드 변경과 Shift+Tab을 비활성화했습니다. 서버 이벤트에 실제 소유 연결의 활성 상태를 포함하고, 화면에서도 연결 이벤트의 기본값을 보완했습니다. 명시적인 `false`는 유지합니다. 기존 테스트는 상태 조회 API가 이 값을 채우는 경로여서 문제를 놓쳤습니다.
3. 반복되는 동일 실행 상태 안내마다 업무 목록 버튼을 다시 만들었습니다. 클릭 도중 대상 버튼이 사라질 수 있어, 안내 문구는 갱신하되 목록은 실행 상태가 달라질 때 갱신합니다. 종료 시작 시에는 별도로 목록 버튼을 비활성화합니다.

로딩 표시는 기존 CSS `transform: rotate()` 애니메이션을 유지합니다. 이번에 직접 재현한 지연은 네이티브 요청 대기열 및 반복 렌더링이며, 모든 PC의 체감 지연 원인이 동일하다는 의미는 아닙니다.

## 검증 결과

- 수정 전 연결 이벤트 회귀 테스트 실패(`connected` 누락)를 확인했습니다. 수정 후 바로 요청하는 경로, 연결 준비 후 요청하는 경로, 종료된 연결의 늦은 이벤트를 통과했습니다.
- 수정 전 반복 진행 안내가 버튼 객체를 교체하는 테스트 실패를 확인했습니다. 수정 후 100회 연속 안내에서도 클릭 대상과 포커스가 유지되고, 완료·종료 시 상태와 버튼이 갱신됩니다.
- 연결·승인·단축키·실행 상태·중지/재개·종료·네이티브 창 관련 통합 테스트 **314개 통과**.
- 실제 WebView2에서 조회 4개를 지연시킨 실험: 버튼 요청 **2,859.7ms → 14.5ms**. 조회와 이전 화면의 이벤트 대기 혼합: **2,842.5ms → 11.6ms**. 업로드가 대기 중인 조건: **17ms**. 네이티브 오류 없음. 이 측정은 특정 지연 조건의 재현이며 전체 앱 성능 향상 비율이 아닙니다.
- 실제 앱 창에서 Computer Use로 합성 작업 시작 → 작업 중 클릭으로 `Plan` → 입력창 `Shift+Tab`으로 `Auto` 전환을 확인했습니다. 동일 작업 ID·`running` 상태·사용자 요청 1개를 유지했습니다. CLI 기록에는 `set_permission_mode(plan)`과 `set_permission_mode(auto)`만 추가됐습니다.
