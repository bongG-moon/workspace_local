# 화면 전환 효과 검증 — 2026-10-18

버전은 0.23.27을 유지했습니다. 이 문서는 구현 단계의 기능·성능 검사 기록입니다. 이후 0.23.27 재빌드의 회귀 검사와 배포 파일 검증은 [통합 배포 검증](VALIDATION_0.23.27.md)에 기록합니다.

## 적용 범위

- 설정·도움말·미리보기 등 네이티브 dialog 열기: 140ms, 투명도와 세로 4px 이동.
- 업무·대화 선택, 홈 및 스킬·기능 화면 표시: 120ms 투명도 전환.
- 자료·결과 탭: 100ms 투명도 전환.
- 닫기·입력·전송에 애니메이션 완료 대기를 넣지 않았습니다. 스트리밍 내용 갱신은 전환 표시를 변경하지 않습니다.
- CSS가 효과를 관리합니다. 새 라이브러리, 지속 타이머, MutationObserver, 레이아웃 강제 읽기, will-change 또는 forwards fill을 추가하지 않았습니다.
- prefers-reduced-motion이 reduce이면 효과를 적용하지 않습니다. 설정 변경은 CSS 미디어 쿼리에 즉시 반영됩니다.

## 기능 검사

`tests.test_workspace_motion`, `tests.test_workspace_frontend_state`, `tests.test_workspace_file_refresh_frontend`, `tests.test_workspace_plain_chat`: **51개 통과**, 실패·건너뜀 없음.

실제 데모 UI에서 라이트·다크 설정 팝업, 업무 간 이동, 일반 대화/업무 이동, 자료/결과 탭과 닫기를 확인했습니다. 브라우저 오류는 없었습니다. 입력 보존은 자동 상태 검사로 확인했습니다. 자동화 입력 중 IME의 추가 조합 문자가 관찰되어 UI 입력값을 정확한 보존 검증 수치로 사용하지 않았습니다.

WebView2 fixture에서 빠른 전환 100회, 입력 즉시 포커스, 닫기 즉시 적용, 스트리밍 텍스트 변경 시 효과 미반복, 종료 후 애니메이션 0개, 동작 줄이기 시 애니메이션 0개를 검사했습니다.

## 성능·메모리 비교

WebView2 155.0.4283.62의 독립 프로필에서 **실제 앱 CSS**를 사용하는 1,000개 메시지·80개 설정 항목 fixture로 검사했습니다. 60회씩 6구간, 총 360회의 팝업·화면·탭 동시 전환을 실행했습니다. 이 중 효과를 켠 구간은 240회 연속입니다. 별도의 100회 빠른 전환과 워밍업 24회는 아래 성능 구간에 포함하지 않았습니다.

- 효과 켜짐 구간의 프로세스 메모리는 첫 꺼짐 구간보다 약 6~13MiB 높았습니다. 연속 구간 후반에는 낮아졌고 최종 꺼짐 구간은 최초 기준보다 낮았습니다. 단기 측정에서 지속 누적은 관찰되지 않았습니다. 비용이 0인 기능이라고 해석하지 않습니다.
- 효과 켜짐 구간의 렌더러 TaskDuration은 60회당 약 537~703ms, 꺼짐은 약 314~330ms였습니다. 세 요소를 동시에 바꾸는 한 회당 추가 메인 스레드 작업은 약 3~6ms 수준이며 애니메이션은 compositor 작업도 사용합니다.

## 측정 한계와 판단

측정은 사용자 환경과 분리한 렌더링 fixture입니다. 실제 대화 서버·Claude·MCP의 전체 메모리나 사내 저사양 PC의 장시간 사용을 측정한 결과는 아닙니다. 테스트 창은 화면 밖에 두고 렌더링을 계속하기 위한 테스트용 background/occlusion 옵션을 사용했습니다. 프레임은 requestAnimationFrame 간격, 메모리는 강제 GC 후 JS 힙과 테스트 WebView2 프로세스 합계입니다. 프로세스 메모리에는 렌더링 캐시와 런타임 변동이 포함됩니다.

이 조건에서 심한 부하나 계속 증가하는 메모리는 관찰되지 않아 짧은 효과를 유지했습니다. 너비·높이 애니메이션, 배경 흐림 애니메이션, 긴 퇴장 효과는 적용 범위에 넣지 않았습니다.
