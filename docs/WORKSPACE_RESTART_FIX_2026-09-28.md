# Workspace 0.11.1 종료·재실행 수정

사용자가 창을 닫고 새 버전을 실행할 때 WS-39가 발생했습니다. 실제 확인 결과 동일한 소스 폴더의 0.10 서버가 남아 있었고 업무는 idle 상태였습니다. 인증된 기존 종료 API로 정상 종료한 뒤 0.11.1 실행기로 다시 시작했습니다. 최신 bootstrap의 버전·실행 폴더·running 상태와 기존 업무 1건을 확인했으며 Claude 실행 확인 오류는 없었습니다. 모델 요청은 보내지 않았습니다.

## 변경

- 다른 버전이 남아 있으면 인증된 기존 창을 다시 열어 정상 종료 경로를 제공합니다. 안내를 실제 UI인 **설정 → 앱 종료**로 수정했습니다.
- 창의 X는 창만 닫는다는 안내를 설정에 추가했습니다. 자동으로 진행 중인 업무를 종료하지 않습니다.
- 앱 종료 요청은 기존 요청을 정리하고 소유한 CLI 종료를 확인한 뒤 완료 응답을 보냅니다. 종료 중 새 변경 요청은 거절하며 읽기 전용 상태 조회는 유지합니다.
- 종료 화면은 설정 대화상자를 닫고 진행 중·완료·확인 실패를 구분합니다. 종료 버튼을 여러 번 눌러 중복 요청하지 않습니다.
- 실행기는 종료 중인 서버와 해당 runtime 기록이 사라질 때까지 기다립니다. 확인이 되지 않으면 새 서버를 겹쳐 시작하지 않습니다.

## 재확인: 실제 사용 중인 압축 해제 폴더

이후 사용자는 앱이 열리지만 WS-39 경고가 계속 나온다고 보고했습니다. 최초 복구 때 저장소 루트의 앱을 실행해 두었으나, 사용자가 실제로 실행하는 위치는 `dist/company-workspace-preview-0.11.1-20260928-214617/Company-Workspace`였습니다. 버전이 같아도 실행 폴더가 다르면 경고를 표시하는 기존 판정이 원인이었습니다.

저장소 루트의 대기 상태 앱을 정상 종료했습니다. 사용자 지정 폴더가 원본 ZIP과 완전히 같은지 확인한 뒤, 해당 폴더의 실행기와 진단 해시를 보완했습니다. 경고 대화상자가 열려 있는 동안 실행 잠금을 유지하던 별도 문제도 수정했으며, 수정 전 두 파일은 `build/workspace-launcher-backup-e2ae4f2f76044cb38ec35e615a06f925`에 보관했습니다.

사용자가 지정한 **정확한 VBS 경로**로 실행하고 다시 실행한 결과 모두 종료 코드 0이었고, bootstrap의 실행 위치가 사용자 지정 폴더인 것을 확인했습니다. 두 번째 실행은 같은 서버 PID를 재사용했고 기존 업무 1건을 유지했습니다. 이 확인 이후 저장소 루트의 앱을 다시 띄우지 않았습니다.

실행 잠금 회귀 및 시작·진단 테스트는 31개 중 29개 통과, 환경 조건 2개 제외였습니다. 추가 수정 ZIP은 `dist/company-workspace-preview-0.11.1-20260928-215434.zip`이며 40개 파일 검사를 통과했습니다. SHA-256: `2db5b67162e0f5a415a9c041303c20adf91ac3e70f0523707cd6f84304be3ab1`.
