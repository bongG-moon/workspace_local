# 0.23.30 성능·구조 점검

점검일: 2026-10-22. 기준: `8d7e644`의 응답성·승인 기본값 개선, 이후 레이아웃 수정과 0.23.30 버전 변경을 포함한 작업 소스입니다.

아래 최초 점검에서 개선 후보를 찾은 뒤, 사용자의 추가 승인에 따라 일부를 구현했습니다. 실제 Edge, 별도 프로필의 숨겨진 WebView2, 격리된 Python LocalApp에 합성 자료를 넣어 검증했습니다. 실제 Claude 요청이나 개인 설정 변경은 하지 않았고, 회사 PC·VDI·MCP 환경의 지연 원인을 확정한 결과는 아닙니다.

## 후속 구현 상태

- **도구 활동 저장:** 화면용 tool/execution 기록을 250ms 단위로 병합하고 별도 작업자 하나에서 공용 앱 잠금 밖으로 디스크 저장을 옮겼습니다. 업무별로 최신 저장 표시만 보관하며, 오래된 스냅샷은 무효화합니다. 중요한 대화·전송 상태는 동기 저장을 유지합니다. 종료 시 남은 저장과 오류를 확인합니다.
- **화면 반복 생성:** 닫힌 전체 업무 팝업을 생성하지 않고 닫으면 요소를 해제합니다. 답변 조각은 스킬 화면 계산을 호출하지 않으며 폴더·연결 메타데이터가 같으면 정렬 결과를 재사용합니다. 업무 폴더 변경 시 자동 조회는 유지합니다.
- **불필요한 조회:** 관리자 프록시는 새 진행 조회가 오면 이전 조회를 취소합니다. POST 변경 요청은 취소하지 않습니다. 이전 화면의 이미지 GET도 AbortController로 정리하고 완료 경로에서 요청 슬롯을 정확히 반환합니다.
- **버전 관리:** `local_app/server.py`의 버전을 원본으로 생성 명령과 모든 빌드의 일치 검사를 추가했습니다. [개발 절차](WORKSPACE_VERSION_MANAGEMENT.md)를 따릅니다.
- **이번에 제외:** 큰 응답의 이벤트 바이트 상한은 사용자 요청에 따라 변경하지 않았습니다. 네이티브 빌드 지문 확대도 이번 범위에 포함하지 않았습니다.

최종 답변·업무 변경의 동기 저장, 상세 SQLite 진행 기록, 파일 관찰은 여전히 잠금과 저장 지연의 영향을 받을 수 있습니다. 이번 수정은 빈번한 화면용 전체 기록 저장을 줄이는 범위이며, 모든 I/O가 비동기화됐다는 뜻은 아닙니다. 강제 종료 직전의 짧은 병합 구간에는 아직 저장되지 않은 화면용 활동 요약이 있을 수 있지만, 대기 요청의 변경·전송 상태를 지연 저장으로 바꾸지는 않았습니다.

검증 결과와 실제 측정 수치는 [검증 기록](VALIDATION_0.23.30.md)에 정리합니다. 아래 수치는 수정 전 원인 분석 자료입니다.

## 우선순위

### 1. 도구 활동 저장과 공용 잠금 — 높음

`local_app/server.py:1674`, `1880`, `339`에서 도구 활동·실행 기록마다 전체 대화 JSON을 저장합니다. `local_app/history.py:243`의 flush/fsync와 파일 교체까지 앱 전체 잠금 안에서 수행합니다. 취소·순서 변경·지금 반영도 `local_app/app_dispatch.py:374`에서 같은 잠금을 기다립니다.

- 한글 50만 자 대화에 도구 활동 30건을 넣으면 전체 기록을 30번, 합계 45,123,508바이트 기록했습니다. 총 685ms, 건당 중앙값 22.29ms였습니다.
- 짧은 대화의 건당 중앙값도 22.91ms여서, 이 로컬 측정에서는 텍스트 길이보다 저장 작업의 영향이 컸습니다.
- 다른 업무의 저장을 테스트용으로 200ms 보류했을 때, 별도 업무의 대기 요청 취소도 저장이 풀릴 때까지 대기했습니다. 잠금의 영향 관계를 확인한 실험이며 사내 디스크 지연 측정은 아닙니다.
- 시작·종료 시 폴더 관찰도 같은 잠금 안에서 실행됩니다. 파일 검사 시간 예산은 느린 단일 파일 접근을 즉시 중단하는 장치가 아닙니다.

권장: 화면용 활동 저장은 세션별로 병합하고 불변 스냅샷을 만들어 공용 잠금 밖에서 기록합니다. revision/runId 확인, 종료·전환 시 flush와 오류 처리가 필요합니다. 대기 요청 claim·전송 상태의 동기 저장과 중복 실행 방지는 유지해야 합니다. 단순히 저장 호출만 별도 스레드로 옮기면 오래된 상태가 최신 상태를 덮을 수 있습니다.

### 2. 닫힌 전체 업무 팝업의 반복 생성 — 중간

`local_app/web/app.js:350`, `380`, `383`에서 업무 목록을 갱신할 때 닫힌 `#all-sessions`도 다시 만듭니다.

| 업무 수 | 현재 목록 갱신 중앙값 | 숨겨진 팝업 갱신만 실험적으로 제외 | 숨겨진 팝업 내부 노드 |
| --- | ---: | ---: | ---: |
| 50 | 15.88ms | 9.86ms | 850 |
| 200 | 50.08ms | 31.72ms | 3,400 |
| 500 | 127.04ms | 84.88ms | 8,500 |

전체 업무 팝업은 열릴 때만 만들고 닫을 때 해제하는 방식이 우선입니다. 이후 사이드바도 업무 ID별 요소를 재사용하면 상태 하나가 바뀔 때 전체 목록을 재생성하는 작업을 줄일 수 있습니다. 위 수치는 로컬 합성 자료의 해당 함수 측정이며 앱 전체 속도 개선율은 아닙니다.

### 3. 관리자 연결의 이전 진행 조회 취소 누락 — 중간

`deploy/Workspace.Desktop.cs:492`의 ProxyApi는 이벤트 조회 슬롯 4개를 사용합니다. 화면에서 이전 fetch를 취소해도 네이티브 HttpWebRequest는 취소되지 않습니다. `app.js:591`의 업무 전환과 `server.py:2399`의 최대 20초 조회 대기가 만나는 경로입니다.

실제 WebView2에 격리된 서버를 연결해 이전 요청 4개를 100ms 후 화면에서 취소했습니다. 이전 서버 응답이 3초 후 끝나는 조건에서, 새 진행 조회는 2,784.4ms 걸렸습니다. 이전 요청이 없는 기준은 44.9ms였습니다. 코드상 20초 대기는 실제 측정값과 구분합니다. HTTP 200, 네이티브 실패는 0건이었습니다.

권장: 업무 전환 세대와 네이티브 이벤트 조회의 취소를 연결해 이전 조회가 슬롯을 반환하도록 합니다. 변경 POST는 별도 경로이므로 자동 취소하지 않아야 합니다. 관리자 프록시에서 재현한 수신 지연이며 일반 실행 전체나 과거 삭제 클릭 문제의 확정 원인은 아닙니다.

### 4. 이전 업무 이미지가 새 이미지 요청을 기다리게 함 — 중간

`local_app/web/rich-content.js:128`, `183`에서 이미지 동시 요청은 2개로 제한되지만 reset은 진행 중 요청을 취소하지 않습니다. 이전 응답 2개를 보류한 상태에서 새 이미지를 만들면 새 요청은 0개이고, 이전 응답이 끝난 후 2개가 시작되는 것을 재현했습니다.

권장: 이미지 요청별 AbortController를 두고 업무 전환 시 취소합니다. 진행 요청 수는 finally에서 정확히 감소시켜야 합니다. 수만 0으로 초기화하면 기존 요청이 살아 있는 동안 동시 실행 제한을 넘을 수 있습니다.

### 5. 이벤트 버퍼의 바이트 예산 부재 — 중간, 큰 응답 조건

`local_app/server.py:1877`의 이벤트 버퍼는 300건으로 제한되지만 총 바이트 제한은 없습니다. 대화의 50만 자 제한과 별개입니다. `bridge.py:27`의 허용 프레임 크기 안에서 약 512KiB delta 32건을 보내면 텍스트 16,777,206바이트, 응답 JSON 16,781,816바이트를 보관·전송했고 직렬화는 33.57ms였습니다.

이는 일반적인 몇 글자 단위 토큰 출력의 대표 성능 수치가 아닌 큰 묶음 응답 스트레스 검사입니다. 세션별·전체 이벤트 바이트 예산과 응답 크기 제한, 보관 범위를 벗어난 클라이언트의 스냅샷 재동기화가 필요합니다. 본문을 임의로 자르거나 승인·종료 이벤트를 누락시키는 수정은 피해야 합니다.

### 6. 스킬 화면의 불필요한 문맥 계산 — 낮음

`app.js:645`, `capabilities.js:49`, `463`: 스킬 화면이 열린 상태에서는 답변 조각마다 업무 폴더 목록을 정렬·재구성합니다. 업무 500개에서 변경 없는 contextChanged 500회는 148ms였습니다. 호출당 비용만으로 큰 지연을 설명하지는 못하지만, 상태가 그대로인 계산은 생략할 수 있습니다.

권장: 연결·업무 선택·업무 메타데이터 변경에만 갱신하고 목록 revision을 기준으로 재사용합니다.

## 구조·배포 유지보수

- **네이티브 빌드 식별:** `local_app/build_identity.py:19`와 PowerShell 대응 함수는 local_app 소스만 포함합니다. 네이티브 창 소스만 바꾸면 식별값이 그대로인 것을 임시 복사본에서 확인했습니다. 같은 버전으로 네이티브만 재배포할 때의 공백입니다. 이번 0.23.30은 버전이 올라가므로 기존 버전 교체 경로를 사용합니다. 이후 배포된 네이티브 호스트의 빌드 식별도 함께 관리하는 편이 좋습니다.
- **버전 원본 중복:** 서버, 시작 스크립트, 진단, 번들 이름에 수동 버전 상수가 분산되어 있습니다. 이번 변경은 모두 맞췄고 진단 해시도 갱신했습니다. 향후 한 버전 원본으로 빌드 시 상수를 생성하면 누락 위험을 줄일 수 있습니다.
- **안내 정합성:** 생성되는 EXE ZIP 안내서의 동일 버전 재사용 설명은 이번에 WS-48의 다른 빌드 확인 동작에 맞게 정정했습니다.

## 이미 갖춰진 제한과 점검 범위

40ms 스트리밍 묶음 처리, 닫힌 이어 할 일 상세 렌더 생략, 대화 150개·50만 자 제한, 동시 Claude 연결 5개, 자료 목록 200개, 활동 요약 80개, 상세 진행 기록 32MiB/세션, 이미지 수 제한과 진행 기록 해제를 확인했습니다. 네이티브 이벤트·일반 조회·변경·업로드 요청 슬롯도 분리되어 있습니다.

이번 조사로 일반적인 메모리 누수나 앱 전체의 무제한 프로세스 누적을 단정할 근거는 없습니다. 이벤트 응답을 쓰는 동안 공용 잠금을 유지하는 구조는 있으나, 읽지 않는 localhost 클라이언트 실험에서 별도 업무 취소 지연은 재현되지 않아 확정 결함으로 분리하지 않았습니다.

최초 점검의 우선순위는 공용 잠금과 저장 → 숨겨진 목록 렌더 → 관리자 조회 취소 → 이미지 취소였습니다. 후속 구현은 위 상태 표를 기준으로 확인합니다. 이벤트 바이트 예산은 이번에 제외했습니다. 이후 실제 운영 추적에서 지연이 남는다면 상세 진행 기록과 파일 관찰을 별도로 측정하고 개선해야 합니다.
