# Company Workspace 설계 명세서

문서 기준: Workspace **0.11.4**, 2026-09-28.

이 문서는 현재 구현이 해결하려는 문제, 구조를 선택한 이유, 실제 기능과 제약을 설명한다. 기능 명세는 소스 코드와 검증 기록을 기준으로 한다. 대안 비교는 현재 구조의 장단점을 설명하기 위한 설계 판단이며, 모든 대안을 구현해 성능을 비교했다는 뜻은 아니다.

## 1. 제품의 목적

Company Workspace는 터미널 명령과 폴더 이동에 익숙하지 않은 사람이 기존 Claude Code를 업무 앱처럼 사용하는 로컬 GUI다.

사용자가 알아야 할 순서는 **업무 공간 선택 → 자료 선택 → 자연어 요청 → 질문·승인 응답 → 결과 확인**이다. `cd`, 실행 명령, 스트림 출력 형식을 먼저 익힐 필요 없이 이 순서로 일을 시작하게 만드는 것이 목표다.

기존에 사용하는 모델, 회사 연결, 인증, 스킬, MCP, 후크는 실제 Claude CLI가 처리한다. Workspace는 그 위에서 입력, 진행 상황, 사용자 판단, 결과 접근을 연결한다.

따라서 “터미널과 같은 기능”은 **같은 실행 환경의 Claude 업무 기능을 GUI로 사용한다**는 의미다. 임의의 PowerShell 명령을 실행하는 범용 터미널 에뮬레이터나 모든 Claude TUI 화면의 복제품은 아니다.

### 핵심 요구와 대응

| 사용자 요구 | 설계 대응 | 확인할 경계 |
| --- | --- | --- |
| 명령어 없이 시작하고 싶다 | VBS 더블클릭, 새 업무, Windows 폴더 선택 | CLI와 승인된 Python 환경은 사전 설치 필요 |
| 기존 Claude와 같은 환경을 쓰고 싶다 | 실제 호출 진입점·환경·작업 폴더를 유지 | 다른 셸이나 임시 환경변수까지 자동 재현하지 않음 |
| 문서를 편하게 주고 결과를 받고 싶다 | 원본 경로 첨부, 자료·결과 패널, 후속 요청 | 선택 완료와 문서 해석 성공은 서로 다름 |
| 지금 무엇을 하는지 알고 싶다 | 준비·실행·질문·승인·완료·오류·중지 구분 | CLI가 제공하지 않은 정보를 추정하지 않음 |
| 어떤 스킬과 도구가 있는지 알고 싶다 | 설치 발견과 현재 연결 정보를 구분하는 카탈로그 | 목록 발견이 권한·접속·실행 성공을 보장하지 않음 |
| 현대적이고 선명한 앱을 원한다 | 뉴모피즘 웹 UI, 일관된 모달, DPI 대응 선택 창 | Windows 탐색 영역의 테마·언어는 OS를 따름 |
| 기존 설정을 망가뜨리고 싶지 않다 | 실행 계정 확인, 설정 재사용, 관리 변경 명시 확인 | 사용자 신뢰·CLI 권한·조직 정책은 별도 경계 |

### 범위 밖인 기능

- 모든 TUI 전용 슬래시 명령과 작업 팀 관리 화면의 완전한 GUI 재현.
- 자체 모델 라우팅, 앱 전용 로그인, 자격증명 보관, 별도 추론 서버.
- 원격 접속, 다중 사용자 협업 서버, 클라우드 동기화.
- 원본 문서의 자동 업로드, 결과의 자동 외부 공유, 자동 게시.
- Windows 보안 정책·UAC 변경이나 조직 실행 제한 우회.

## 2. 주요 구조를 이렇게 선택한 이유

### 2.1 기존 Claude CLI를 실행 엔진으로 사용

이미 정상 동작하는 회사 모델 연결과 사용자 설정을 앱에서 다시 구현하면 동일성을 유지하기 어렵다. 인증 방식이나 설정 우선순위를 두 곳에서 관리하면 “터미널에서는 되지만 앱에서는 안 되는” 원인이 늘어난다.

Workspace는 CLI의 입출력만 `stream-json`과 제어 메시지로 연결한다. CLI가 기존 인증·모델·스킬·후크·MCP를 읽고 작업을 수행하므로 업무 실행 책임이 한곳에 남는다.

실행 파일을 발견했다는 사실과 실제 인증·모델 응답 성공은 구분한다. 연결 재확인은 `--version`, `--help`를 검사하며 사용자 요청을 재전송하거나 확인용 추론을 자동 실행하지 않는다.

근거: [bridge.py](../local_app/bridge.py), [Invoke-TerminalClaude.ps1](../local_app/Invoke-TerminalClaude.ps1).

### 2.2 Python 로컬 서버와 Edge 앱 창

현재 제품은 Python 표준 라이브러리의 HTTP 서버와 HTML/CSS/JavaScript 화면으로 구성한다. 서버는 `127.0.0.1`의 임의 포트에만 열리고, Edge가 있으면 `--app` 방식으로 독립 창을 띄운다. Edge를 찾지 못하면 기본 브라우저로 연다.

이 선택은 별도 브라우저 엔진을 묶지 않고 기존 Windows·Python·브라우저 환경에서 작은 배포 묶음으로 시작할 수 있게 한다. 화면 수정과 CLI 연결 코드의 책임도 분리된다.

반대로 설치형 앱의 창 수명주기와 OS 통합을 모두 얻지는 못한다. 창의 X와 서버 종료가 분리되고, VBS·PowerShell 허용 여부에 영향을 받는다. 이것은 현재 구조의 명시적 비용이다.

| 대안 | 얻을 수 있는 점 | 현재 구조와 비교한 비용·판단 |
| --- | --- | --- |
| CLI 화면 그대로 제공 | 구현 범위가 작고 고급 기능에 직접 접근 | 명령·폴더·출력 해석 부담이라는 원래 문제를 해결하기 어려움 |
| 모델 API에 직접 연결 | 자체 UX와 실행 흐름을 폭넓게 통제 | 기존 CLI 인증·권한·스킬·MCP 재현과 호환성 유지 책임이 커짐 |
| Electron 등 설치형 셸 | 창 종료·파일 대화상자·자동 업데이트의 통합 설계 가능 | 추가 런타임, 설치·서명·업데이트 체계가 필요해 현재 미리보기 범위를 넘어감 |
| 현재의 로컬 웹 UI | 기존 실행 환경 재사용, 작은 묶음, 빠른 화면 개선 | 브라우저와 백그라운드 서버 수명주기를 별도로 다뤄야 함 |

설치형 셸로의 이전은 향후 선택지다. 현재 구현이 모든 배포 환경에서 더 우월하다는 주장은 하지 않는다.

### 2.3 Company Agent 관리 기능은 등록된 설치에 위임

기억·지식·업무 구성은 Workspace 안에 복제하지 않는다. 현재 Claude 설정 루트와 작업 폴더에 맞는 Company Agent 설치 등록을 확인한 뒤, 그 설치의 Python과 로컬 관리 API를 호출한다.

프로젝트 범위가 더 구체적인 등록을 우선하되 같은 범위가 겹치면 임의로 하나를 선택하지 않는다. 설치가 없거나 관리 API가 없는 구버전이면 해당 기능의 확인 필요 상태를 표시하고 일반 Claude 대화를 유지한다.

이 구조는 UI와 개인 자산 저장 규칙이 서로 다른 기준으로 동작하는 것을 줄인다. Workspace 업데이트와 Company Agent 업데이트는 별도이며, 하나의 업데이트가 다른 설치를 자동 변경하지 않는다.

근거: [harness_client.py](../local_app/harness_client.py), [companion.py](../local_app/companion.py).

### 요청 한 번의 흐름

1. 사용자가 업무 공간의 실행 범위를 확인하고 요청과 첨부 경로를 선택한다.
2. 브라우저가 실행별 토큰을 붙여 로컬 API에 JSON을 보낸다.
3. 서버가 업무 상태·신뢰·폴더·첨부를 검사하고 파일 메타데이터를 관찰한다.
4. CLI 어댑터가 해당 폴더를 `cwd`로 사용해 기존 Claude를 시작하거나 이어 간다.
5. CLI의 응답·질문·승인·실행 상태를 업무별 이벤트로 변환한다.
6. 화면은 이벤트 순번을 기준으로 변경 내용을 받고, 질문·승인 답을 제어 메시지로 돌려준다.
7. 완료·실패·중지 시 파일을 다시 관찰하고 UI 기록과 결과 목록을 갱신한다.

별도 모델로 제목·요약·라우팅을 생성하지 않는다. 첨부는 사용자 요청 뒤에 원본 경로의 JSON 표현을 덧붙여 전달하며, 파일을 임시 저장소로 복사하지 않는다.

## 4. 화면과 상호작용 명세

### 4.1 업무 중심의 화면 구성

홈은 빈 채팅만 보여 주지 않고 자료 정리·보고서·발표·자유 요청의 시작 예문과 최근 업무를 제공한다. 예문은 입력창만 채우고 전송은 사용자가 결정한다.

새 업무는 앱이 관리하는 새 공간 생성과 기존 폴더 사용을 분리한다. 관리 공간의 실제 폴더명은 날짜와 식별자로 만들며, 사용자가 입력한 업무 이름을 파일 시스템 경로로 해석하지 않는다.

대화 화면은 중앙의 요청·응답과 자료·이번 결과 패널을 연결한다. 결과에서 바로 후속 요청을 만들 수 있어 사용자가 파일 경로를 다시 입력하는 부담을 줄인다.

고정·검색·이름 변경으로 여러 업무를 구분한다. 홈의 최근 목록은 짧게 유지하고 **전체 업무 보기**에서 모든 저장 업무를 검색한다. 좁은 창에서 왼쪽 목록이 숨겨져도 이전 업무로 이동할 수 있다.

### 4.2 뉴모피즘을 쓰되 상태를 그림자에만 맡기지 않음

밝은 배경, 부드러운 양방향 그림자, 눌린 입력면과 보라 계열 강조색으로 친숙한 앱의 질감을 만든다. 동시에 테두리, 텍스트 상태, 키보드 초점, 선택 속성을 함께 사용한다.

자료·결과 탭의 강조는 `aria-selected`를 기준으로 하나만 표시한다. 긴 파일명은 확장자 배지와 분리해 영역 안에서 줄바꿈한다. 화면 폭에 따라 자료 패널을 따로 열도록 하며 좁은 화면에서도 업무와 입력에 접근할 수 있게 한다.

화면 스타일은 [app.css](../local_app/web/app.css), 업무 동선은 [app.js](../local_app/web/app.js)에서 구현한다. 다른 서비스의 코드나 브랜드 자산을 제품 구성 요소로 사용했다는 뜻은 아니다.

### 4.3 확인·오류·취소의 일관성

앱 내부의 확인은 공통 HTML 대화상자를 사용한다. 기본 초점은 취소에 두고 Esc를 취소로 처리하며, 닫힌 뒤 호출한 버튼으로 초점을 돌려준다.

확인 전에는 기존 초안과 도우미 화면을 유지한다. 확인을 기다리는 동안 업무나 화면이 바뀔 수 있으므로 실행 직전에 대상 상태를 다시 확인한다. 비동기 업무 선택 응답도 최신 선택인지 확인한다.

오류 안내는 가장 위에 열린 대화상자 안에 표시한다. 본문 위의 모달 때문에 경고가 뒤에 숨는 상황을 피하기 위한 규칙이다.

이 설계는 예쁜 확인창 자체보다 **사용자가 취소했을 때 작업 맥락을 잃지 않는 것**을 우선한다. 근거: [0.11.4 검증 범위](VALIDATION_0.11.4.md).

### 4.4 고해상도 파일·폴더 선택

파일과 폴더는 Windows `IFileOpenDialog`를 사용한다. 폴더는 폴더 선택 모드, 파일은 문서·이미지 필터와 다중 선택을 사용한다. 제목·선택 버튼·필터 설명은 앱이 한국어로 지정한다.

선택 창과 임시 부모 창을 만들기 전에 Per-Monitor V2를 우선 적용하고 Windows 시각 스타일을 켠다. 지원되지 않는 환경에서는 가능한 DPI 방식으로 대체한다. Windows 전체 배율이나 호환성 레지스트리는 바꾸지 않는다.

선택 버튼을 누른 시점의 전면 창을 Workspace 제목으로 식별할 수 있으면 그 창과 연결한 임시 부모 창을 사용한다. 식별하지 못하면 독립 부모 창을 사용한다. 한 번 앞으로 표시한 뒤 상시 최상위를 해제한다. 다른 앱으로 이동한 사용자의 초점을 반복해서 가져오지 않는다.

선택 중 중복 호출을 막고 취소는 빈 경로 목록으로 반환한다. COM 객체와 경로 메모리를 정리하며 한글·공백·이모지 경로를 그대로 전달한다. 시작 경고창에도 같은 DPI 초기화를 사용하되, 보조 코드 실패가 원래 오류 안내를 막지 않게 한다.

## 5. 업무·연결 상태 명세

| 상태 | 의미 | 주요 UI 동작 |
| --- | --- | --- |
| `idle` | 저장 업무를 열었거나 재시작 후 대기 | 폴더 신뢰를 다시 확인하고 시작 |
| `starting` | CLI 연결과 요청 준비 | 중복 전송 방지, 진행 안내 |
| `running` | CLI가 작업 중 | 부분 응답 표시, 중지 가능 |
| `question` | 사용자 질문에 대한 답 필요 | 단일·다중 선택과 직접 입력 |
| `approval` | CLI가 실행 판단 요청 | 대상·변경 내용·실행 원문과 승인·거절 |
| `done` | CLI가 완료를 보고 | 응답과 관찰된 결과 확인 |
| `error` | 연결 또는 요청 오류 | 원인과 다음 행동 안내, 자동 재전송 없음 |
| `stopped` | 연결 중지 확인 | 남은 결과 확인, 만료 승인 제거 |

같은 업무의 요청은 동시에 실행하지 않는다. 살아 있는 CLI 연결은 최대 3개다. CLI가 보고한 작업자 시작·상태·완료 이벤트를 추적하며, 실행 중인 작업자가 남았다고 보고된 경우 중간 result를 전체 완료로 표시하지 않는다. 별도 OS 프로세스의 생존 상태를 직접 검사한다는 뜻은 아니다.

부분 응답은 설치된 CLI가 해당 옵션을 지원할 때만 사용한다. 메시지 ID와 블록 인덱스로 최종 응답과 합쳐 중복 표시를 줄인다.

현재 연결의 모델 변경은 초기화가 끝난 대기 연결에서만 가능하다. CLI의 제어 응답을 확인한 뒤 반영하며 영구 모델 설정을 바꾸지 않는다. 연결이 종료되면 임시 선택도 해제된다.

## 6. 스킬·도구 카탈로그 명세

### 두 종류의 근거를 구분

**현재 연결에서 확인**은 선택한 업무의 CLI가 실제로 보고한 스킬·도구·MCP 서버·명령이다. **설치에서 발견**은 해당 작업 폴더에 연결된 Company Agent 설치와 스킬 메타데이터를 읽어 얻은 목록이다.

설치 조회는 검증된 설치의 인터프리터에서 제한된 범위의 메타데이터를 읽는다. 탭 열기나 새로고침으로 모델 요청, 도구 실행, 설정 변경을 하지 않는다. 작업 폴더 신뢰가 없거나 설치를 확정하지 못하면 이유를 표시한다.

설치된 스킬을 모두 현재 실행 가능하다고 표시하지 않는다. 실제 연결이 로드한 정보와 발견만 된 후보를 함께 보여 주되 출처를 남긴다.

| 분류·상태 | 표시 규칙 |
| --- | --- |
| 일반 스킬 | 호출 이름이 있으며 사용자 호출이 가능한 항목 |
| 내부 보조 스킬 | `user-invocable: false`; 별도 접힌 영역에 표시 |
| 참조 자료 | 호출 이름이 없음; 슬래시 명령을 임의로 만들지 않음 |
| 직접 호출 전용 | `disable-model-invocation: true`여도 사용자 호출 가능하면 일반 스킬에 포함 |
| 동일 이름 | 정규 호출 이름·플러그인 구분을 유지해 다른 출처를 잘못 합치지 않음 |
| 검색 결과 | 표시 행만 필터링하며 상단의 확인된 일반 스킬 총수는 유지 |
| 연결 전 | 아직 현재 연결의 목록 근거가 없음 |
| 미확인 | 연결됐지만 CLI가 해당 목록을 제공하지 않음 |
| `0` | 빈 목록임을 실제로 보고받은 경우에만 표시 |
| 마지막 연결 정보 | 종료된 연결에서 마지막으로 확인한 값임을 명시 |

서버 연결 상태와 도구 이름이 보여도 개별 실행 권한이나 성공을 보장하지 않는다. 근거: [기능 목록 코드](../local_app/capabilities.py)와 [공개 검증 기록](VALIDATION_0.11.4.md).

## 7. 신뢰·승인·로컬 보안

### 7.1 폴더 신뢰와 실행 승인은 다른 판단

폴더 신뢰는 그 위치의 Claude 설정·후크·MCP가 적용될 수 있음을 확인하는 절차다. 재시작하면 이전 업무의 신뢰를 자동 복구하지 않고 다시 확인한다.

실행 승인은 CLI가 현재 요청에 대해 보내 온 판단 항목이다. 일반 파일 읽기·쓰기·편집은 대상과 변경 내용을 설명하고, 임의 명령이나 외부 도구의 의미는 추측으로 안전하다고 표시하지 않는다.

승인은 해당 요청에 대한 응답이다. 앱은 자동 승인, 권한 우회, 샌드박스 해제 옵션을 추가하지 않는다. 기존 CLI 정책이 이미 허용한 도구는 별도 승인창 없이 실행될 수 있다.

### 7.2 로컬 API 경계

- 서버는 loopback에만 바인딩하고 실행마다 새로운 토큰을 만든다.
- 모든 `/api/` 요청은 Bearer 토큰을 검사한다. Host, 제공된 Origin, cross-site 요청 여부도 검사한다.
- 최초 주소의 토큰은 브라우저가 읽은 뒤 주소에서 제거하고 탭의 `sessionStorage`에 둔다.
- 토큰을 포함한 로컬 접속 정보는 재열기를 위해 `runtime.json`에도 보관한다. 배포·게시 대상이 아니다.
- JSON POST 본문은 256 KiB로 제한한다. 응답은 `no-store`, 콘텐츠 유형 보호와 CSP를 적용한다.
- HTTP 접근 로그에 주소·인증 토큰·파일 경로를 남기지 않는다.

이 경계는 외부 웹 페이지나 잘못된 요청이 로컬 API를 사용하는 위험을 줄인다. 같은 Windows 계정에서 실행되는 악성 프로그램까지 차단하는 별도 격리 환경은 아니다.

### 7.3 파일과 실행 환경

GUI의 파일 열기는 작업 폴더 또는 사용자가 첨부한 정확한 경로와 지원 확장자로 제한한다. 저장된 폴더의 실제 위치 변경·연결 경로를 확인하며 파일 탐색에서 링크를 따라 무제한으로 내려가지 않는다.

모델 출력은 실행 가능한 HTML로 넣지 않는다. 지원 HTML의 정적 미리보기는 스크립트·외부 연결을 막고, 일반 HTML은 소스로 보여 준다. HTML 원본을 OS 연결 앱으로 실행하는 API도 허용하지 않는다.

GUI의 파일 접근 제한은 Claude 자체의 권한·샌드박스를 대체하지 않는다. 첨부를 고르는 즉시 업로드하지 않지만 실제 요청의 자료 처리는 기존 Claude·회사 모델 연결을 따른다. 로컬 UI가 오프라인 추론을 뜻하지 않는다.

실행기는 본인 계정·프로필·세션을 검증한다. 관리자 권한을 상속했다면 같은 사용자의 기존 일반 권한 토큰으로 재실행을 시도하며 계정이나 UAC 정책을 바꾸지 않는다. 해당 토큰이 없는 WS-33 환경의 제한은 남아 있다.

## 8. API 계약 개요

아래는 프런트엔드와 로컬 서비스 사이의 내부 계약이다. 외부 원격 서비스용 공개 API나 장기 호환 SDK를 제공한다는 의미는 아니다. 업무 대상 요청은 업무 `id`를 사용한다.

| 방식·경로 | 입력·출력 요약 | 주요 제약 |
| --- | --- | --- |
| GET `/api/bootstrap` | 앱·CLI 버전, 업무 목록, 실행 위치, 종료 상태 | 실행 파일 확인과 모델 인증 성공을 구분 |
| GET `/api/session` | 업무와 대화, 현재 연결, 질문·승인 | UI에 필요한 제한된 상태 |
| GET `/api/events` | 업무 ID, `after` → 순번 이후 이벤트 | 최대 20초 대기, 메모리의 최근 이벤트 사용 |
| POST `/api/create` | 폴더 또는 관리 공간, 신뢰, 제목 → 새 업무 | 최대 500개, 제목 1~100자 |
| POST `/api/session/update` | 이름·고정 여부 변경 | 실행 폴더 변경 API가 아님 |
| POST `/api/trust` | 현재 폴더 명시 확인 | 실제 폴더 위치 재확인 |
| POST `/api/send` | 요청·첨부 경로 → 전송 | 요청 32,000자, 첨부 최대 12개, 동시 실행 제한 |
| POST `/api/respond` | 요청 ID, 승인·거절, 질문 답 | 현재 연결의 유효한 요청에 응답 |
| POST `/api/stop` | 업무 연결 중지 | 완료된 파일·외부 작업의 되돌리기가 아님 |
| POST `/api/reconnect` | CLI 실행 환경 재확인 | 활성 작업 종료·실패 요청 재전송 없음 |
| POST `/api/model` | 모델 이름 또는 기본값 복원 | 지원되는 대기 연결만 변경 |
| POST `/api/pick` | 파일·폴더 모드 → 원본 경로 목록 | Windows, 한 번에 하나의 선택 창 |
| GET `/api/files`, `/api/results` | 자료 목록·관찰 결과 | 깊이·확장자·개수·시간 제한 |
| GET `/api/preview` | 허용된 경로 → 텍스트·이미지·정적 HTML | 1 MiB 초과 또는 Office/PDF는 원래 앱 안내 |
| POST `/api/open` | 허용된 문서를 연결 앱으로 열기 | Windows, HTML 원본 실행 차단 |
| GET `/api/capabilities` | 현재 연결과 설치된 기능 정보 | 조회로 AI·도구 실행 없음 |
| GET `/api/course` | 첫 업무 따라 하기 과정 | 정적 학습 자료 |
| GET·POST `/api/companion` | 관리 조회·검토·저장 | 신뢰·활성 설치 확인, 실행 중 일부 변경 제한 |
| POST `/api/native` | 원본 CLI 열기·세션 이어받기 | 같은 업무의 GUI 연결을 먼저 중지 |
| POST `/api/quit` | 앱 소유 연결 정리 → 종료 결과 | 정리 성공 뒤 `closed: true`; 실패 시 503 |

## 9. 데이터와 저장 명세

기본 Workspace 상태 루트는 `%LOCALAPPDATA%/CompanyAgent/local-ui`다. 사용자 지정 상태 경로가 있으면 이를 사용한다. 프로그램 폴더와 사용자 기록을 분리해 프로그램 파일 교체가 곧 업무 기록 초기화가 되지 않게 한다.

| 데이터 | 저장 위치·형태 | 보존·의미 |
| --- | --- | --- |
| 실행 정보 | `runtime.json` | 현재 접속 주소·실행 토큰·PID·포트; 정상 종료 후 본인 기록만 제거 |
| 업무 목록 | `history-index.json` | 최대 500개 업무, 식별자·제목·폴더·시각·고정·CLI 세션 ID |
| UI 대화 사본 | `history-sessions/<업무 ID>.json` | 대화당 최근 최대 150개 메시지, 본문·경로 합계 50만 자 제한 |
| 결과 관찰 | 업무별 기록의 `artifacts` | 생성·수정으로 관찰한 경로·크기·시각·요청 ID, 최근 최대 100개 |
| 앱 생성 업무 폴더 | `workspaces/<날짜와 식별자>` | 사용자가 만든 실제 업무 자료·결과 저장 |
| 학습 확인 | `learning-progress/<폴더 해시>.json` | 제한된 자기 확인 기록; 업무 성공의 자동 판정이 아님 |
| 초안·실시간 이벤트·승인 | 메모리 | 초안은 화면 이동 간 유지, 재시작 복구 없음; 신뢰·승인 영구 저장 안 함 |
| Company Agent 개인 자산 | 활성 설치가 지정한 별도 상태 루트 | 개인 전체·프로젝트 범위를 구분, Workspace 기록과 합치지 않음 |
| Claude 원본 기록 | 기존 CLI가 관리하는 저장소 | Workspace의 제한된 사본과 별개 |

기록은 임시 파일 작성과 교체 방식으로 저장한다. 손상된 기록을 발견하면 원본을 보존하고 새 앱 기록 저장을 중지한 사실을 알린다. 기존 `history.json`은 다음 정상 저장 시 이전하되 자동 삭제하지 않는다.

개인 기억·지식·지침 변경은 미리보기, 명시 확인, 현재 내용 해시 재확인을 거친다. 실행 중인 업무와 충돌하는 변경은 보류한다. 저장 응답이 시간 초과하면 결과를 미확인으로 안내하며 자동 재시도하지 않는다.

## 10. 결과·사용량을 과장하지 않는 규칙

“이번 결과”는 요청 전후의 파일 크기·수정 시각 차이를 관찰한 목록이다. 모델이 해당 파일을 만들었다는 감사 기록이나 요청과 변경의 인과관계 증명은 아니다.

관찰 범위는 작업 폴더와 바로 아래 하위 폴더의 지원 문서다. 파일·디렉터리 수와 탐색 시간에 한도를 두고 제한·오류를 표시한다. 삭제 파일, 더 깊은 폴더, 외부 첨부 위치의 결과를 모두 수집하지 않는다.

텍스트·이미지는 앱에서 미리 보고 Office·PDF는 연결된 원래 앱에서 확인한다. 읽기·미리보기·열기 기록과 내용의 정확성 검증은 구분한다.

사용량은 CLI 보고값과 사용자가 선택한 로그 분석을 구분한다. 누락은 미제공으로 표시하고 사내 모델 비용을 임의로 추정하지 않는다. 서로 중복되거나 누적일 수 있는 값은 무조건 합산하지 않는다.

## 11. 시작·종료·배포 명세

같은 사용자·상태에서 이미 서버가 실행 중이면 인증된 상태 응답의 버전과 실행 폴더를 확인한다. 같은 버전·폴더면 기존 창을 다시 열고, 다른 버전·폴더면 기존 창으로 돌아가 종료할 수 있게 안내한다.

오래된 runtime 파일만으로 프로세스를 종료하지 않는다. 시작 잠금은 오류 안내창이 열린 동안 다른 정상 실행을 계속 막지 않도록 해제한다.

창의 X는 브라우저 창만 닫는다. **설정 → 앱 종료**는 서버가 새 변경 요청을 막고 이미 접수한 요청을 정리한 뒤 소유 CLI 연결의 종료를 확인한다. 읽기 상태 조회는 정리 중에도 유지한다.

종료를 확인하지 못하면 완료로 표시하지 않는다. 실행기는 종료 중인 서버와 runtime 기록이 사라질 때까지 최대 45초 기다리며, 확인되지 않으면 새 서버를 겹쳐 시작하지 않는다.

중지는 앱이 소유한 실행을 대상으로 한다. 이름이 같은 다른 Claude·Office 프로그램을 찾아 종료하지 않는다. CLI 트리 종료가 실패하면 모든 하위 외부 프로그램까지 종료됐다고 보장하지 않으며 이미 완료된 작업을 되돌리지 않는다.

배포는 명시한 파일 목록으로 미리보기 ZIP을 만든다. 0.11.4 실행 묶음은 42개 파일이며 사용자 기록·실행 정보·개인 설정·인증 정보는 포함하지 않는다. 소스와 ZIP의 파일 일치 및 시작 코드 진단 해시를 확인한다.

새 ZIP 생성, Git 저장소 게시, 사용 중인 압축 해제 폴더 적용은 각각 별도 작업이다. 자동 업데이트·설치 서명·중앙 배포는 현재 구현되어 있지 않다. 실행 조건은 Windows, 승인된 Python 3.11 이상, 사용 가능한 기존 Claude CLI다.

## 12. 검증 기준과 현재 확인 범위

| 검증 층 | 확인 대상 | 성공으로 주장할 수 없는 것 |
| --- | --- | --- |
| Python 회귀 | API 경계, 기록, CLI 제어, 시작·종료 경합, 카탈로그 | 실제 회사 인증과 문서 품질 |
| 프런트 상태 회귀 | 지연 응답, 초안 보존, 승인·취소, 업무 전환, 개수 표시 | 모든 브라우저·접근성 조합의 인증 |
| 격리 브라우저 검증 | 가상 업무·가상 CLI의 실제 화면, 좁은 창, 오류·확인창 | 실제 모델이 파일을 생성했다는 증거 |
| Windows 네이티브 API | DPI 모드, 시각 스타일, COM 옵션, 경로 반환, 창 생명주기 | 모든 모니터 배율에서의 최종 외관 |
| 패키지 검증 | 허용 파일 목록, 소스 일치, 해시, 개인 상태 제외 | 직원 PC에 자동 적용됐다는 증거 |

0.11.4 UI 보완 당시 기록은 서로 다른 자동 테스트 122개 중 **119개 통과, 환경 조건 3개 건너뜀**이다. 가상 업무의 실제 브라우저에서 확인창, 팝업 오류, 긴 이름, 좁은 창의 전체 업무 검색과 종료를 확인했다.

파일 선택·시작 경고창의 DPI 초기화는 실제 Windows API로 검증했으나 네이티브 창의 최종 외관을 모든 배율에서 직접 검증한 것은 아니다. 사내 HCP 인증, DRM·Office 실제 자료 처리, 직원 PC 정책은 별도 환경 검증이 필요하다.

119/3 수치는 UI 보완 당시 변경 묶음의 기록이다. 별도 공개 저장소로 분리하면서 수행한 전체 Workspace 회귀 테스트와 외부 Company Agent 통합 검증은 [0.11.4 공개 검증 기록](VALIDATION_0.11.4.md)에 구분해 기록한다. 테스트 통과가 전체 제품의 무결성이나 실제 회사 업무 성공을 보증하지는 않는다.

## 13. 확장 시 유지할 원칙

현재 구조를 확장하더라도 사용자 설정의 주인은 기존 CLI와 등록된 Company Agent라는 원칙을 유지한다. 새 GUI 기능 때문에 모델·인증·MCP·개인 기억을 임의 초기화하지 않는다.

설치형 셸로 옮긴다면 창 X와 서버 종료 정책, 네이티브 대화상자 소유권, 서명·업데이트를 먼저 명시한다. 일반 브라우저보다 앱처럼 보인다는 이유만으로 업무 프로세스의 종료를 추정하지 않는다.

기능 목록을 확장할 때는 발견·설정 활성·런타임 로드·실행 성공을 계속 구분한다. 작업 결과를 확장할 때는 단순 파일 관찰을 넘어선 근거가 있을 때만 생성 주체나 성공을 표시한다.

일상 사용 설명은 [사용 가이드](LOCAL_WORKSPACE.md)를 따른다. 이 명세서와 실제 동작이 달라지면 관련 API·저장·권한·검증 항목을 함께 갱신한다.
